# @triage/web

Next.js 16 (App Router) app for Triage.

## Environment

From this app directory, create the local env file:

```sh
cp .env.example .env.local
```

Set `MODEL_API_KEY` (and `OPENROUTER_API_KEY` / `FIREWORKS_API_KEY` for hosted open weights) here, not at the workspace root. Each stage's provider and model is chosen in Settings → Models; see the root README. Never commit `.env.local`.

## Scripts

```sh
pnpm dev        # http://localhost:3000
pnpm build
pnpm start
pnpm lint
pnpm typecheck
pnpm test             # unit and agent-loop tests, no model calls
pnpm check:blind      # nothing Triage can read gives the planted bug away
pnpm check:sandbox    # proves known-good fixes for the planted faults in the sandbox and checks the real database is unchanged, no model calls
pnpm benchmark        # root cause found rate, control false positives, median time and cost per model (see Investigation agent)
pnpm check:uptime     # opens and investigates an uptime incident by hand (see Endpoint checks)
pnpm export:incidents # writes incidents, settings and checks back out as JSON files
```

## Endpoints

- `GET /api/health` returns each stage's provider, model and any problem, the Lead's included, and whether investigations fan out (`{ ok, fanout, stages }`), without calling a model.
- `GET /api/ping-model?stage=<id>` (or `?provider=<id>&model=<id>`) calls that model once and returns `{ ok, text, usage }`.
- `GET`/`PUT /api/settings/models` read and change each stage's model and the local/custom endpoints (keys are write-only). `GET /api/settings/models/list?provider=<id>` lists a provider's chat models.
- `POST`/`GET`/`DELETE /api/mcp` is Triage's MCP server (see MCP server).
- `POST /api/investigations` with `{ "scenario": "pool-leak" | "price-gap" | "live-ratings" | "bad-deploy" | "traffic-rush" | "vulnerable-dependency" | "healthy" | "live" }` (a recorded scenario, or `live` for the running Shopfront) starts an investigation and returns `{ id }` (202). The agent runs after the response and saves progress to its row in `.data/triage.db` (gitignored; see Storage below); open `/incidents/<id>` to watch it.

## Watch (Stage 1)

`src/lib/investigation/watch.ts` starts with the server (`src/instrumentation.ts`) and watches the live store. Every 10 s it judges each enabled watch rule on every route the rule covers, over the rule's window of real requests (the same telemetry the investigation reads). A rule measures p95 latency, a count of slow requests, the error rate, or an SLO's burn rate (below), on API routes, pages or both, with its own severity. Rules are edited on the Watch page and saved in `.data/watch-rules.json`; the defaults (`watch-rule-model.ts`) are **API SLO**, **Page latency** (more than 10 requests slower than 1500 ms in a minute on a page, for a minute) and **Server errors** (more than 5% errors on any route), with **API latency** (p95 over 500 ms) kept as a paused example.

- **Opening:** a rule over its limit for its checks in a row (2 by default, 6 (a minute) for Page latency, with at least its minimum requests) opens an incident with `openedBy: "watch"` and runs the whole pipeline. Page latency waits out a burst: a dev server's renders after it sat idle or restarted, or after a fault is turned off, come a few a minute (3 or 4 on /products/[id], up to 8 on / on Nov 4 2026), which "more than 3 for 2 checks" paged on with a chart that never crossed its line; the pool leak is 21 to 60 a minute and pages 70 to 80 s after it starts. An SLO rule opens when an alert fires (see SLOs).
- **What an incident charts:** the rule's own measure, per minute, on the route that tripped it (`tripMetric`): its p95 (`http.server.request.duration.p95{route=…}`), its count of slow requests (`http.server.slow_requests{route=…,le=1500}`) or their share in percent (`http.server.slow_share{…}`), its error ratio, or the SLO's burn rate. The recovery watch and Verify judge that same series, so an incident recovers by the measure that opened it. A "more than N" rule breaches only past its limit: under "more than 10 slower than 1500 ms", a minute with 10 slow requests is healthy. (Until Nov 3 2026 a slow-request rule charted the route's p95 against the slow limit, which on a page with a few requests a minute stays high on one slow render; incidents from before keep that trigger.)
- **One incident per outage:** each rule has its own episode: it opens one incident and re-arms after a minute of its own healthy checks. Rules tripping in the same check, or within 10 min of an incident opening while a rule in it is still over its limit, join that incident (the most severe opens it; `joinedRules` on the incident), as long as it isn't resolved or archived: a breach after a resolution goes through Reopening below, never silently into the closed incident. An SLO's fast alert judges a quiet route only once its short window holds enough requests, so it can fire minutes late, after the outage's other rules have re-armed: within those 10 min it still joins their incident when the minutes it is burning on overlap that incident's breach, from its first check over the limit to its last. Those minutes are the newest run of minutes each over the alert's threshold on its own (up to 2 clean minutes in a row between them), back to where that burn began within the long window; only the newest run, so an earlier outage in the window isn't counted. A slow burn never joins late (its 6 h window overlaps anything), and a burn that began after the other breach ended opens its own. A rule tripping later opens its own, so an SLO's slow-burn tail doesn't hide a new fault on another rule. Nor on its own routes: an SLO's fast alert (14.4× or 6×) that fires after its fast alerts have been quiet for 30 min (the 6× alert's short window, `FAST_BURN_QUIET_MS`) starts the rule's next episode. It opens a new incident at the rule's severity, joins another rule's incident from the last 10 min, or reopens the SLO's own incident resolved in the last 30. A fast alert that clears and fires again sooner is the same outage, and the slow alert's trips stay in whatever episode is open.
- **UI:** the sidebar shows its state (`GET /api/watch`, polled every 5 s), toasts when it opens an incident, and pauses or resumes on click (`POST /api/watch`, in memory).
- **Off switch:** `TRIAGE_WATCH=0` keeps it off.
- **Restarts:** at startup, incidents a restart cut off mid-run are marked failed (`recover.ts`). The watch rebuilds each rule's episode from the newest unresolved incident it opened or joined; the rule's next trip joins it rather than opening a new one, and the episode is dropped once the rule re-arms. For an SLO rule, a fast alert already firing at its first check after the restart is the outage still going and joins it; if the fast alert was quiet then, it counts as last firing when the incident opened, so a fast burn 30 min or more after that opens a new incident.
- **Reopening:** a breach on a rule whose incident was resolved (or whose verification breached) in the last 30 minutes reopens that incident instead of opening a new one, unless that incident's mitigation is still in effect; see Verify.

### SLOs and burn-rate alerts

A watch rule can be an SLO instead of a fixed limit: it pages on how fast a route's error budget burns, the way the SRE Workbook's "Alerting on SLOs" does, rather than on one bad minute. The pieces are under `src/lib/slo/`.

- **The rule:** an objective (99, 99.5, 99.9, 99.95 or 99.99% in the editor; 50 to 99.999 in the file) over 7, 28 or 30 days, where a request is good when it didn't fail (no 5xx, no span error) and, optionally, took at most 100, 250, 500, 1000 or 2500 ms. Each route the rule covers has its own budget, as each route is judged on its own by the other rules. The rule's window and checks in a row don't apply; its minimum requests is per alert, over the alert's long window; the short window needs enough that one bad request alone can't fire it (70, 167 and 1000 at 99.9% over 30 days), and never fewer than the minimum scaled to its length.
- **The alerts:** each fires on a route when the burn rate (the bad share over the share the objective allows; 1× spends exactly the budget over the window) is over its threshold in both its windows, so it stops soon after the burn does. A short window with only a handful of requests doesn't judge: after a cold start, with an old outage still in the 6 h window, one slow first visit once paged at 200×. The thresholds are shares of the budget, so they scale with the window; over 30 days they're 14.4×, 6× and 1×:

  | Spends | Long and short window | 30 days | Opens |
  | --- | --- | --- | --- |
  | 2% of the budget | 1 h and 5 min | 14.4× | at the rule's severity |
  | 5% | 6 h and 30 min | 6× | at the rule's severity |
  | 10% | 3 days and 6 h | 1× | sev4, after it has fired for 5 min |

  The slow burn waits because it's a ticket, not a page, and because a big outage keeps the 3-day burn near 1× for days: without the wait it fired on the next outage's first bad minute and opened it at sev4 a minute before the fast alert could. A fast burn anywhere wins over a slow one. After a big outage the slow alert keeps firing while its 6 h window holds the bad minutes, and the watch counts that as the SLO rule's episode, so the SLO re-arms only once that clears. A new outage in that tail still pages: a fast alert after 30 min without one opens a new incident (see One incident per outage), and other rules open their own as usual.
- **The incident:** titled with the burn rate ("Error budget burning 83.3× on GET /api/products/[id]"), charting the route's burn over the last 5 minutes, per minute (`slo.burn_rate{route=…,objective=…,le=…}`, built from the spans on request), against the threshold that fired, so Verify resolves it once the burn stays under it. `trigger.burn` keeps the burn, the threshold, both windows, the budget left and, for a fast alert, the minutes it is burning on (`burning`, the watch's run of minutes above, e.g. 03:32 to 03:49). The investigation's brief says them, and that earlier outages in the alert's long window are not this incident. Without the minutes (a slow burn, an incident from before) it points at the short window instead, and when they began more than 30 min before the alert it says to widen the tools' window. On 2026-11-04 the 6× alert on the price list gap was investigated as the pool leak its 6 h window also held.
- **Request counts:** the telemetry only reaches back 3 hours, so `slo/rollups.ts` counts each route's requests per UTC minute (total, failed, and good within each latency above) into `request_minutes`, and summarises each complete hour into `request_hourly`, in `.data/triage.db`. Minutes are kept 4 days (the 3-day window and its edges), hours 90. Every 10 s it rewrites the last 5 settled minutes (those that ended 30 s ago), so late spans count and nothing is counted twice; the first pass after a start writes every minute still in the telemetry, and never rewrites minutes the telemetry no longer holds. It starts with the watch (`TRIAGE_WATCH=0` keeps it off) but the sidebar's pause doesn't stop it: a pause stops alerting, not the budget. The watch judges an SLO on the counts plus the requests since the last minute written.
- **Default:** **API SLO**, 99.9% of API requests succeeding within 500 ms over 30 days at sev2 with at least 100 requests per window, listed first; a full outage pages in under a minute on a route with at least 70 requests in 5 min (about 14 a minute), and a quieter route pages on the 6 h alert within a few minutes. **API latency** (p95 over 500 ms) stays in the defaults, paused. Saved rules (`.data/watch-rules.json`) keep what they hold.
- **UI:** Measure → Error budget (SLO) in the rule editor, with what the objective leaves to spend ("0.1% of requests, about 43 min of full outage in 30 days") and the alerts read back. The rule's page says its budget and alerts in words. Its backtest replays the last 24 hours of request counts every 10 s with the live watch's episodes, a fresh fast burn in a tail included (`slo/backtest.ts`). The service page's **Error budget** section has a card per SLO: the budget left on its lowest route, the burn over 1 h and 6 h, the requests it's counted on (a budget on a few dozen swings far on one bad one), a burndown across the window, and its routes; the Routes table gains a Budget column. `/api/live` carries them as `slos`, recomputed at most every 10 s.

## Endpoint checks

Beside the traffic rules, Watch can check public URLs from the outside, so a site with no SDK, logs or telemetry connected still gets an incident when it goes down or slow. `src/lib/investigation/uptime.ts` runs with the watch (the sidebar's pause and `TRIAGE_WATCH=0` cover both); the pieces are under `src/lib/investigation/uptime/`.

- **A check:** a name, a URL (`http:` or `https:` only, no userinfo), optionally a header to send for an endpoint behind a token (its name, `Authorization` by default, and a secret value), how often (10 to 300 s, default 30), the slow limit (default 10 s), the timeout (default 15 s), the status range that counts as a good answer (default 200 to 299), how many slow checks in a row open an incident (default 3), how long with no good answer opens one (1 to 30 min, default 5), and how many healthy checks in a row confirm recovery (2 to 10, default 3). Up to 5 checks, saved in `.data/triage.db` with the rest of Triage's state (see Storage below).
- **A result:** a GET timed to the response headers (the body is never read), with redirects followed by hand up to 5 hops. The outcome is `ok` (a status in range within the slow limit), `slow` (in range, past it) or `down` (a timeout, a DNS, TLS or connection failure, a status out of range, too many redirects, or a hop the guard refused). A timeout counts as down, never as slow.
- **Two rules per check:** Slow trips when the last N results are all slow and opens a sev3 incident ("Slow responses from www.example.com"); Down trips when the newest result is down and the unbroken run of down results has lasted the whole window, and opens a sev2 incident ("www.example.com is not responding", or "www.example.com is rejecting the check's credentials" when every result of the run was a 401 or 403). Down wins when both trip. The rule is on the incident as `trigger.rule` (`uptime:<checkId>:slow` or `:down`, described as "3 checks in a row slower than 10 s on …" or "no acceptable response for 5 min from …"), the URL as `trigger.route`. Slow charts the check's response time against the slow limit; Down charts availability per minute (the share of checks that were ok) against 100 %, so the chart shows the drop.
- **One incident per episode:** later failing checks only count on the open incident (`incident.uptime`: the check, the rule, `failedChecks`, `lastFailedAt`, written at most once a minute), shown on the page's Endpoint check card. A Slow episode whose endpoint then stops answering for the whole Down window becomes the Down incident: the same incident is retitled, raised to sev2 and charted as availability, with the Down rule on it. A trip within 30 min of the incident being resolved reopens it, as the traffic rules do. At startup the loop finds the open uptime incidents again, so a restart in mid-outage opens nothing new. Pointing a check at another URL starts it over: its results are dropped and an incident open on the old target stays for a person to close.
- **What it investigates:** a `TelemetrySource` over the check's own results (`uptime/source.ts`): `uptime.response_time{check=…}` and `uptime.availability{check=…}` as metrics, the failures grouped by error as error logs, one span per check, and nothing else, with each empty tool saying the endpoint is external. The prompt tells the model so and that an `inconclusive` verdict naming what is missing (application logs, traces, a deploy history) is the right answer when the results alone cannot say why; no fix stage runs. When the check's origin is `SHOPFRONT_URL` (default `http://localhost:3001`), the live source joins in: Shopfront's telemetry, database, code and deploys plus the check results, and the whole pipeline runs (mitigation, fix, PR) from an incident the check opened. `run.source` is `uptime:<checkId>`, so Ask Triage can read the saved results again.
- **Recovery:** confirmed by the checks, never assumed. Once the check has answered in time the configured number of times in a row, the incident is resolved with a `verification` of `after: "uptime"` (its series the healthy checks, in the incident's own metric) and the resolution is notified. It waits while the investigation is still running (recording `uptime.recoveredAt`, then resolving on a later tick) and while a mitigation's own verification is watching; a run that failed does not hold it up. The verification card reads "N healthy checks" rather than a quiet window.
- **Notifications:** the same `notify` as the traffic rules, so the Slack preferences and the once-per-event log apply: opened, reopened and resolved. The resolved line reads "Triage confirmed it: 3 checks in a row answered in time."
- **Credentials:** the header's value never leaves the server. The routes return a check with the header's name alone; a save that comes back without the value keeps the saved one, as long as the check still targets the same origin (pointing it at another host asks for that host's token); the probe sends the header to the check's own origin only, never along a redirect elsewhere. A 401 or 403 is recorded as `HTTP 401: credentials rejected` / `HTTP 403: forbidden`.
- **Safety:** the guard (`uptime/guard.ts`) runs before every request and every redirect hop. It refuses anything but http and https, userinfo in the URL, and any hostname that is, or resolves to (every address of the lookup), a loopback, private, carrier-grade NAT, link-local, unique-local, multicast, unspecified or reserved address, IPv4-mapped IPv6 included; a save with such a URL answers 400 with the reason. `TRIAGE_UPTIME_ALLOW_PRIVATE=1` lets loopback and private targets through outside production, for a local demo on Shopfront; link-local stays refused (it is where cloud metadata services answer). Best-effort: `fetch` resolves the name again when it connects, so a DNS answer that changes in between is not caught. At most 5 checks and one request in flight per check keep the load bounded.
- **History:** results live in SQLite, `.data/triage.db` (gitignored), through Node's built-in `node:sqlite`, which is why Triage needs a current Node (24 or later, see the root README's Setup; `src/lib/db.ts` opens it, sets WAL mode and runs numbered migrations). Every result is kept raw for 48 hours; each complete UTC hour is summarised (checks, ok, slow, down, average and slowest response) and kept for 90 days, written before that hour's raw results are deleted, in one transaction (`uptime/samples.ts`, pruned at most every 10 minutes). The judge, the page and investigations still see the last 500 results. Uptime per window (`uptime/history.ts`) counts each hour's summary, or its raw results while it has none; slow counts as up, and the figure is floored, so 100% means nothing was down. Results from before this change, one `.data/uptime/<id>.json` per check, move in on first open and the file is deleted once its rows are saved; a file that can't be read stays.
- **Routes:** `GET`/`PUT /api/watch/endpoints` read and replace the list (`PUT` runs the guard on every URL, answers 400 naming the check and the reason, and drops a removed check's results); `GET /api/watch/endpoints/<id>` returns the check, its live state, its last 50 results and its uptime over 24 h, 7 d and 30 d; `POST /api/watch/endpoints/<id>/check` runs it now and returns the result (404 unknown, 409 while one is in flight). `GET /api/watch` carries every check's state as `endpoints` (status `healthy`, `slow`, `unavailable`, `unchecked`, `alerting` while its incident is open, or `paused`; the summary, streaks and the open incident's id).
- **UI:** the Watch page's **Endpoints** section lists the checks with their status, last result and a strip of the last 20 results; **New endpoint**, and each check's page with its configuration in words, a response-time chart, the last 50 results, **Check now**, **Edit** and **Delete**. The sidebar row uses its second line for a check in trouble ("Google · slow, check 2 of 3", "Google · down 3 of 5 min") and lists the checks in its tooltip. An uptime incident's Overview shows the Endpoint check card: the URL, the rule in words, failing checks so far or the recovery time, and a link to the check.
- **By hand:** `pnpm --filter @triage/web check:uptime google`, or `TRIAGE_UPTIME_ALLOW_PRIVATE=1 pnpm --filter @triage/web check:uptime shopfront` (Shopfront is on loopback), opens an uptime incident and investigates it without the loop: fabricated outages on a Google check (expect `inconclusive`), or real probes of Shopfront's health during the planted fault (expect a root cause). It needs `MODEL_API_KEY`.

**Storage.** Triage keeps its state in one SQLite file, `.data/triage.db` (gitignored, `src/lib/db.ts`): incidents (`investigation/store.ts`: the incident as JSON plus indexed columns and a small summary that the list pages read, so a list never parses whole incidents; every change goes through `patchIncident`, one transaction), the settings and uptime checks (`src/lib/documents.ts`), the notification log (`notifications/log.ts`), the uptime history above and the request counts SLOs are judged on (see SLOs). Question images, run snapshots and benchmark output stay as files under `.data/`. Before Nov 2 2026 incidents, settings, checks and the notification log were JSON files in `.data/`; each moves in the first time the database is opened, is read back, and only then is deleted (a file that can't be read stays). `pnpm --filter @triage/web export:incidents` writes them back out as those files.

## Dependency advisories

The third thing Watch keeps an eye on is the watched service's own third-party code. `src/lib/investigation/dependencies.ts` runs with the watch (the same pause and `TRIAGE_WATCH=0`); the pieces are under `src/lib/investigation/dependencies/`.

- **The audit:** the service's own package manager, `pnpm audit --json` (or `npm audit --json`, picked by the lockfile nearest the service), run from the workspace root with a 60 s timeout, output capped at 1 MB, and an environment without Triage's keys (registry settings stay). In a workspace only the service's importer counts (`apps__shopfront>…`), so Triage's own advisories never show up. A finding is one advisory: the package, every version the tree holds, the vulnerable and patched ranges, severity, CWE, the GHSA link, and the chains from the service's own dependencies down to it (runtime chains first). It is **runtime** when any chain starts at one of the service's `dependencies`, **dev** when all of them start at `devDependencies` (`audit.ts`).
- **Schedule:** every 6 h by default (1 to 24 h), plus **Audit now** on the Watch page; one audit at a time. Settings are the `dependency-audit` document (on/off, interval, severity floor, a service directory other than `SHOPFRONT_DIR`). A failed audit (offline, a registry error) is recorded with its error and shown; the findings stay as the last audit that ran left them, and nothing opens.
- **What opens an incident:** a runtime finding at or over the severity floor (default **high**): critical opens a sev2, high a sev3. Dev-only and lower findings are listed on the Watch page and open nothing. One incident per advisory, rule id `deps:<service>:<GHSA id>`, route the package, with an `incident.dependency` block (the finding, plus `audits`, `lastFoundAt`, `goneAt`). Its trigger is `vulnerable_dependencies{advisory=…}`, one point per audit (1 while found). Later audits count on it; the same advisory coming back within 30 days of a resolution reopens it.
- **Exposure stage:** a dependency incident skips the telemetry investigation and runs a short model stage on the investigate stage's model (`exposure.ts`): `list_files`, `read_source` and `grep_source` over the service's source, with the advisory as evidence. The model says whether the vulnerable package is **reachable** from the service's code, **transitive only**, or **not reachable** in production, citing the importing lines; Triage builds the report around it (the vulnerable version as the root cause, the other two exposures ruled out), so the usual fix gate opens. No mitigation is proposed: there is no flag or deploy to undo.
- **Fix and proof:** the Fix stage's dependency mode (`fix.ts`, no model) raises a direct dependency's range in the service's `package.json` to the lowest release in the patched range, or adds an override in the workspace's `pnpm-workspace.yaml` for a transitive one (pnpm 12 reads overrides only there), flagged when it crosses a major version. The proof (`sandbox.ts`) installs the bumped tree in a sandbox of its own (no linked `node_modules`), then re-audits it (the advisory must be gone), typechecks and runs the app's tests: five runs on the incident, from "Audit before the bump" to "Tests". No patched release declines the fix. The PR cites the advisory, the exposure and the proof, regenerates the lockfile in its worktree, and targets the deployed release's branch when the package came in with one, else the default branch.
- **Verification:** a merged dependency PR starts `after: "dependencies"`: the next audit (it runs at once) that no longer finds the advisory resolves the incident; each one that still does adds a note (pull and install the merge). An advisory that disappears another way resolves its open incident with a note saying so.
- **Routes:** `GET /api/watch/dependencies` (state, findings with gone ones for a week, recent audits), `PATCH /api/watch/dependencies` (settings), `POST /api/watch/dependencies/audit` (Audit now). `GET /api/watch` carries the state as `dependencies`. MCP: `get_incident` includes the advisory and the exposure; `list_dependency_findings` lists what is vulnerable.
- **UI:** the Watch page's **Dependencies** section (last and next audit, counts by severity, each finding with its chains, advisory link and incident, settings in place, CSV/JSON export); the advisory card and the Exposure block on the incident page, the bump on the Fix tab; an advisory count on the service's row.
- **Storage:** `dependency_audits` (each audit, the package manager's JSON on the latest only) and `dependency_findings` in `.data/triage.db`.
- **Demo:** deploy Shopfront's **Vulnerable dependency** release from `/ops` (semver 7.5.1, GHSA-c2qf-rxjj-qqgw), then **Audit now**. On Nov 3 the live run went from the audit to a proven bump to 7.5.2 awaiting approval in about a minute. Benchmark scenario `vulnerable-dependency`: 20/20 on Spark (median 15 s, $0.02 a run).

## Mitigation

After a live run's root-cause verdict, `mitigation/propose.ts` proposes one fast, reversible step from the evidence the diagnosis cites, by rule and without a model call. When the rule finds nothing to undo, the incident records why (`noMitigation`: the cited flag is already off, the cited deploy was already rolled back, or the diagnosis cites no change at all, as when the load itself is the cause) and the Mitigation card says so instead of staying empty; the MCP incident text carries the same line. A person approves or denies it on the incident's Mitigation card; `mitigation/decide.ts` runs it through the executor for the run's source (`mitigation/executors.ts`) and then watches the alert's metric until it recovers (see Verify). Two kinds:

- **`flag_off`:** when the cited deploy history shows a flag turned on, when the blamed code checks one (`isEnabled("FF_X")`), or when a flag went on between the blamed deploy and the alert. A flag the logs show is off now (Shopfront's `flags: loaded` at boot plus the `ops: FF_X turned on|off` flips since, read through the source's `describe().flags`, which the alert brief shows the model too) is never proposed, since the code behind it isn't running; the proposer falls through to the next rule instead. On Shopfront the executor posts `{ action: "flag", name, enabled: false }` to its ops API and, when the diagnosis cites a full pool, recycles the held connections.
- **`rollback`:** when the leading hypothesis cites a code deploy, a `deploy_history` record with a real sha rather than a `config:` flip or an earlier rollback, and no flag was turned on after it. On Shopfront the executor reads the ops state, posts `{ action: "rollback" }`, and Shopfront's release harness reverse-applies the deployed release's diff. It succeeds only when the answer's `release` is null and reports `rolled back <sha>`, naming the mitigation's sha too when another release was the one deployed; nothing deployed is a failure. The deploy record's branch is kept on the mitigation as `branch`, and the fix PR is opened against it (see Pull request).

The live source turns Shopfront's `deploy: ...` warnings into deploy and rollback records (`deploy.sha`, `deploy.kind`, `deploy.branch`) beside the `ops: FF_X turned on|off` flag flips, and while a release is deployed (`GET /api/ops` says, read once per source) `git_log` reads history from the release's commit rather than HEAD, so the commit a deploy record names is there to read. The release harness's files (`src/lib/releases.ts`, `releases/`, `scripts/release.ts`) join the demo harness Triage never shows. The executor is picked by the run's source (`executorFor`): a live Shopfront run, or an endpoint check on Shopfront's own origin, gets the real ops API; an endpoint check on any other site gets none, so approving a mitigation there fails with a reason rather than pretending; and on a recorded scenario or a bundled example the simulated executor changes nothing and replays that scenario's recorded recovery (each bundled example its own).

## Verify

After the mitigation's recovery, `src/lib/investigation/verify.ts` checks that the fix worked: it keeps reading the alert's metric for a quiet window and resolves the incident, or reopens it when the metric climbs back. Nothing else sets `resolved` but this loop and a person.

- **The window:** `RESOLVE_AFTER_MINUTES` completed minutes under the alert's threshold after the recovery, 5 by default (`TRIAGE_RESOLVE_AFTER_MINUTES` in `.env.local` to change it). On a live run it reads the metric every 15 s over the last 10 min, as the recovery watch does, and counts the minutes that start after the recovery; a minute with no requests neither counts nor breaks the window. An endpoint check's incident is read the same way from the check's own saved results (`liveReader` in `recovery.ts`), one value per minute, so a Verify on it never resolves from anything but real checks. On a metric where lower is worse (an endpoint's availability), "under the threshold" reads "at or over" it, and a breach is a minute under it; on a slow-request rule's "more than N", it reads "at or under", and a breach is a minute past N. It gives up after the window plus 10 min and records the verification as `stopped` with a note. A scenario replay or bundled example has no live metric: it replays the recorded recovery's later points, padded with a quiet value to fill the window, one minute every 15 s, so the loop is visible but short.
- **What resolves:** every minute in the window under the threshold. The incident gets `status: "resolved"` and `resolvedAt` (the last quiet minute), `verification.status` is `resolved`, the header badge reads Resolved, and the Overview chart shows the recovery, the window and a resolved marker. While it runs, the header reads Verifying (its tooltip counts the quiet minutes) and the mitigation card's Verifying step counts them ("1 of 5 min under 500 ms", or "1 of 5 min at or under 3 requests" for a slow-request rule).
- **What reopens:** the first completed minute at or over the threshold (past it, for a slow-request rule's "more than N"). `verification` ends `breached` with the minute (`breachedAt`) and its value (`breachValue`), a reopening by `verification` is added to `incident.reopenings`, and the status goes back to `awaiting_approval` if a fix approval is pending, else `diagnosed`. The mitigation card says "Back over the limit at 02:17 (… 3022 ms): reopened" and offers Verify again. A reopened incident keeps its report, mitigation and fix, isn't investigated again and doesn't re-apply the mitigation; the header shows Reopened, the chart a reopened marker, and the Overview a notice with who reopened it, when, why and whether the fix still waits for approval.
- **The watch reopens:** once an incident is resolved and its rule has re-armed (only the rule that opened it reopens it; a rule that joined it opens its own), a new breach on the same rule and route within 30 min of `resolvedAt` (or of the verification's `breachedAt`) reopens that incident instead of opening a second one (`reopen.ts`, `REOPEN_WINDOW_MINUTES`): a reopening by `watch`, `lastOpened.reopened` on `GET /api/watch`, and a "Reopened <title>" toast. The route is `trigger.route` (older incidents: the end of the title). An incident whose recovery or verification is still being watched counts too: the breach joins it, and the verification records it. Past 30 min a new incident opens as before. Not while the resolved incident's mitigation still holds: the flag it turned off is still off, or the release it rolled back isn't deployed again (read from Shopfront's ops API, `mitigation/in-effect.ts`; when it can't be read, the mitigation is presumed still in effect). The old cause is then held off, so the breach most likely has a new one: a new incident opens and is investigated as usual, with `relatedTo` naming the old one. The Overview reads "Related to <title>. Same rule and route, resolved 27 min before this opened, with its mitigation (FF_STOCK_DIRECT_QUERY off) still in effect, so this breach was investigated as a new cause.", and MCP `get_incident` carries the same line. A mitigation never applied, or undone since, reopens as before, whoever resolved the incident.
- **After a merged PR:** while the fix's draft PR is open and the incident isn't resolved, loading the incident page checks it with `gh pr view <url> --json state,mergedAt` at most once a minute per incident (`fix/pr-merge.ts`, no background polling; each outcome is logged once as `[triage] PR check on <id>: …`). A merged PR saves `approval.prMergedAt` and starts a verification from the merge time. The demo never merges Triage's PRs, so this path rarely runs.
- **A pending fix approval survives resolution:** Resolved means the alert is verified gone, not that the fix shipped. Approve and Deny stay offered, the incident stays under Needs attention (and in the bell filter) while the approval is pending, and deciding it keeps the status resolved.
- **By hand:** the header's "More actions" menu offers Mark resolved (any finished incident not yet resolved), Reopen (a resolved one; a dialog with an optional note) and Verify (when there is no verification yet; Verify again when the last one breached or stopped); the command palette has the same as "Mark resolved", "Reopen incident" and "Verify" or "Verify again". They call `POST /api/incidents/<id>/resolution` with `{ "action": "resolve" | "reopen" | "verify", "note"?: "…" }` (note up to 300 characters). `resolve` returns `{ status, resolvedAt }`, `reopen` `{ status }`, `verify` 202 and runs a fresh window from now after the response (not from the last recovery, so a breach since then doesn't end it at once). It answers 400 on a bad body, 404 on an unknown incident and 409 when the action makes no sense: resolving a resolved incident or one with no report yet, reopening one that isn't resolved, verifying while a verification runs or before the report.
- **Restarts:** at startup a verification a restart cut off is marked `stopped` ("Triage restarted before the verification finished") and the mitigation card offers Verify again; a recovery watch cut off is marked `not_recovered` with the same kind of note ("Not recovered · the watch stopped" on the card) instead of spinning forever.
- **Postmortem:** the header says resolved with the time, the timeline adds the verification, each reopening and the resolution, and the durations add Time to resolve (first breach to `resolvedAt`). A postmortem written before the incident resolved shows "Written before the incident resolved" beside Write again.

## Ask Triage

Once an incident has a report, its **Ask** section (also "Ask Triage" in the command palette) takes follow-up questions such as "Why was the cache ruled out?" or "Show me the slowest request", with suggestions built from the report. "Is p95 latency back under the limit?" is offered only when Ask can see past the alert (below); otherwise, after a mitigation, "What did the mitigation change?".

- **What it answers from:** the incident (alert, verdict, leading and ruled-out hypotheses, mitigation and fix state), its recorded evidence and the last 6 questions and answers, plus what happened after the alert from the record (`ask/after-alert.ts`): the mitigation's approval, apply time and output, the recovery watch's per-minute series and outcome, each verification's window, series and outcome, reopenings and resolution. The recovery and verification series are citable (`ev_q<n>_recovery`, `ev_q<n>_verification`), and the ones an answer cites are saved with it. When the run's telemetry can be read again, the agent also has the investigation's read-only tools, and their results become the question's own evidence (`ev_q<n>_…`). On a live run or an endpoint check they read up to now, at most 2 hours past the alert (`askSourceFor` in `source-for.ts`), so "is it back to normal?" is answered from fresh telemetry; database checks stay as they were at the alert, and recorded scenarios and bundled examples stay at their recording. Evidence from the investigation stops at the alert, and the prompt says so, so a question about later is answered from the record or those tools, never from the alert's own readings. Every claim cites an evidence ID; cited IDs that don't exist are listed on `unknownIds` and struck in the answer instead of shown as chips.
- **Evidence-only mode:** a bundled example (or any incident whose run can't be rebuilt) answers from the recorded evidence alone, with no tools (`mode: "evidence_only"`). The first question on a bundled example saves a copy of it to `.data/`.
- **Model:** the **Ask** stage in Settings → Models (`src/lib/investigation/ask/agent.ts`). Until it is changed it uses the Investigate stage's model. The composer's model picker changes it for one question without touching Settings.
- **Full context:** the composer's Full context switch answers in one call to Muse Wonder (1M-token window) instead of with tools. Triage reads everything it holds on the service into the prompt (`ask/full-context.ts`), up to 800k tokens: Shopfront's source in 40-line chunks, its git history with every diff, the deploy history, every earlier incident's report, then the telemetry up to the alert. Each item has an evidence ID the answer cites (`ev_ctx_source_…`, `ev_ctx_commit_…`, `ev_ctx_incident_…`), and only the cited items are saved with the question. The bundle depends only on the incident, so later questions on the same incident are served from Meta's prompt cache. The picker is hidden while it's on.
- **Web search:** the composer's Web search switch gives the answer Meta's hosted web search (Meta models only), to look up a library's public docs and cite them; the incident's own data never goes into a search (`web-search.ts`). Cited pages show as evidence like the rest.
- **Context window:** each answer has a card showing how full the model's context window was and what filled it: instructions, tools, the incident report, evidence, earlier questions, the question and any screenshot, plus on a full-context answer the source, git history and deploys, earlier incidents and telemetry.
- **Screenshots:** paste, drop or attach (paperclip) one PNG, JPEG, GIF or WebP per question, such as a Grafana panel or an error page. The browser shrinks it (`src/lib/images/shrink.ts`: long side 1,600 px, WebP, under 900 KB) and sends it as `multipart/form-data` (`text`, `image`, `width`, `height`); with no text the question is "What does this screenshot show, and does it match the incident?". The server checks the type by its bytes and the size (1 MB), saves it to `.data/question-images/<incident>/<question>.<ext>` (served at `GET …/questions/<qid>/image`, not stored in the incident's JSON) and records `image` on the question. The model gets it as an image part with that question only, inline (no Files API, so nothing stays at Meta); a follow-up's history says "with a screenshot" instead of resending it. It describes what the screenshot shows in words, cites evidence IDs for the system, and says so when the screenshot doesn't match the incident. Every Meta model Triage offers reads images; a model that can't fails the question with a hint to pick another.
- **Streaming:** `POST /api/incidents/<id>/questions` with `{ "text": "…" }` (or the form above, with a screenshot) returns a UI message stream over SSE (header `x-question-id`), so the asking tab shows tool calls and the answer token by token. The same deltas are saved to `incident.questions` at most every 300 ms, and the stream is consumed to the end even if the tab closes: a reload or another tab shows the answer growing, and closing the tab mid-answer still leaves a complete answer.
- **Voice input:** with **Voice input** on in Settings → General → Speech (off by default, per browser), a mic button sits left of Send. Speech is transcribed by Meta's **Muse Voice Transcribe** (`muse-voice-transcribe-1.0`) with `MODEL_API_KEY`, at about $0.18 per hour of audio, and streams into the composer as it's heard. The mic button stops and leaves the text to edit, Enter stops and sends, Escape drops it; **Send when transcription finishes** sends on stop. The browser records 16-bit 24 kHz PCM (an AudioWorklet and `src/lib/speech/pcm.ts`) and relays it through `/api/speech/transcribe` (a `GET` that streams the transcript as SSE, then a `POST` per ~200 ms of audio), so the key stays on the server, which holds Meta's realtime socket (`wss://api.meta.ai/v1/asr/realtime`, push-to-talk) in `src/lib/speech/realtime.ts`. A session ends after 5 minutes.
- **Keyword biasing:** the session opens with the incident's service, route and host names as Meta's `keywords`, so "shopfront" stops coming out "shop front". They are sent as the words a person says (`/api/products/[id]` → "products", `www.portionary.app` → "portionary"), since Meta drops punctuation from keywords and `portionary.app` then came out "portionaryapp". `src/lib/speech/keywords.ts` builds them from the alert, the focus, HTTP spans, metric evidence and span hosts (at most 20); Meta fixes them for the whole session, so each dictation opens its own.
- **Read aloud:** the speaker button under each answer reads it with the browser's own voices (the Web Speech API: no server, no key, nothing leaves the browser). Citations and markdown marks are dropped before reading, so the voice says the prose, not `[ev_…]`. One answer plays at a time across the app: pressing another speaker, or the same one again, stops it. The voice and speed are chosen in Settings → General → Speech (per browser, saved in `localStorage`, with a preview); the button is hidden in a browser without speech synthesis.
- **Limits:** one question answering per incident at a time (a second gets 409), 500 characters per question, 10 model steps per answer with one nudge if it stops without text, and a 5-minute run budget (10 minutes with full context). Every tool is read-only; an answer can point at the mitigation or fix cards but never acts.

## MCP server

Triage is also an MCP server, so a coding agent can read its incidents from the terminal: `/api/mcp`, Streamable HTTP, stateless (`src/app/api/mcp/route.ts`, tools in `src/lib/mcp/server.ts`). In Muse Code, add it to `~/.config/muse/settings.json` and run `/mcp` in a new session to check it loaded:

```json
{
  "schema_version": 1,
  "mcpServers": {
    "triage": { "transport": "streamable_http", "url": "http://localhost:3000/api/mcp", "mode": "optional" }
  }
}
```

`"mode": "optional"` lets Muse Code start with a warning when Triage isn't running. Any MCP client that speaks Streamable HTTP works the same way (Claude Code: `claude mcp add --transport http triage http://localhost:3000/api/mcp`).

| Tool | What it returns |
|---|---|
| `list_incidents` | Incidents newest first, filtered by `status` (open, resolved, all) and `service`, with a one-line headline each |
| `get_incident` | The cited report: summary, verdict and causal chain with `[ev_…]` citations, the hypotheses ruled out and why, the alert, mitigation, fix, resolution, and one line per cited evidence item. `id` can be `"latest"` |
| `get_evidence` | Evidence in full by `ids` or `kind` (the report's citations by default, at most 20), each with the tool call that found it; series cut to 24 points, code to 80 lines, rows to 20 |
| `get_fix` | The fix's summary, risk, data change, regression test, sandbox runs and the patch as a unified diff; `attempt` picks an earlier, denied one |
| `get_postmortem` | The postmortem as Markdown (`postmortemMarkdown`), once written on the page |
| `list_dependency_findings` | What the latest dependency audit finds vulnerable, with each advisory's incident (see Dependency advisories) |
| `ask_incident` | Asks a follow-up question, answered like the page's Ask (same stage, limits and tools, up to a few minutes) with progress per tool call; the question is saved on the incident with `via: "mcp"` and the page marks it "From a coding agent" |

- **Read-only:** every tool but `ask_incident` only reads, and none changes the system: approving a mitigation or a fix stays on the incident's page, with a person. Commit authors are never shown.
- **Access:** without `TRIAGE_MCP_TOKEN` it answers only on a loopback host, and refuses a browser `Origin` that isn't one (DNS rebinding). With it set (a hosted Triage), every request needs `Authorization: Bearer <token>`: add `"headers": { "Authorization": "Bearer …" }` to the Muse Code entry. Links in answers use `TRIAGE_URL` when set, else the request's origin.

## Postmortem

Once an incident has a finished report that isn't healthy, its **Postmortem** section (also "Write the postmortem", "Go to Postmortem" and "Copy postmortem" in the command palette) writes a blameless postmortem from the incident's record on request. It shows on the page as the document it exports, with **Copy Markdown** and a **Download** menu (Markdown, PDF, and the action items as CSV or JSON); the Overview links to it once it's written.

- **What the model writes:** with the default template, a summary, one impact sentence, how the diagnosis held up (Triage grading its own verdict against what the record later showed), 2 to 5 contributing factors, what went well and what didn't, where we got lucky, and action items (each a kind: fix this, prevent the class, detect sooner, mitigate faster; and a priority). Every claim cites evidence IDs from the incident; cited IDs that don't exist reject the submission.
- **What the renderer adds from the record:** `postmortemMarkdown(incident)` (`postmortem/render.ts`, no model) builds the header (service, severity, status, when it was detected and written), the impact numbers from the alert's series (peak, time over the threshold, baseline), the timeline from the incident's own timestamps (threshold crossed, alert, investigation, verdict, mitigation proposed, approved, applied and recovered, fix attempts, approval and PR) with time to detect, diagnose, mitigate and recover, the fix as action item 1 with the PR link, and an Evidence appendix of the cited items. Citations are numbered as the page's evidence chips, so `[3]` in the export is chip 3 on the page.
- **Template:** which sections a postmortem has, and in what order, is a template: the eight built-in sections (summary, impact, timeline, how the diagnosis held up, contributing factors, what went well, where we got lucky, action items) reordered or removed, plus custom ones, each a name and instructions, up to 20 sections in all. One template for the whole app, edited in **Settings → Postmortems** (add built-ins back, add and edit custom sections, **Restore defaults**) and saved as `postmortemTemplate` in the settings (`.data/triage.db`); `GET`/`PUT`/`DELETE /api/settings/postmortem` read, replace and reset it (a bad template answers 400 with the problems). The header and the Evidence appendix are fixed. The model writes only the sections the template keeps (the tool's schema is built from it) and fills a custom section from the record, saying so when the record is silent; custom sections are cited and checked for blame like the rest. Each postmortem keeps a snapshot of the template it was written with (`postmortem.template`, its custom sections in `postmortem.custom`), so changing the template reshapes only the next write, never an older document; one written before templates existed renders as the default.
- **Checks:** `postmortem/rules.ts` (custom sections included) turns back a submission that names a commit author or an approver, uses blaming phrases ("blame", "fault of", "should have", "failed to", "careless", "negligent"), cites evidence in the summary, repeats the fix as an action item, or says the diagnosis held when the record shows it didn't. A rejected submission goes back to the model with the reasons, within 3 model steps (one nudge if it stops without submitting); if none is accepted the postmortem is marked failed with the reasons and the section offers Write again.
- **Route:** `POST /api/incidents/<id>/postmortem` returns 202 and writes after the response, saving the record as `incident.postmortem` (status `writing`, then `ready` or `failed`). It answers 409 while the incident is investigating, on a healthy run, while a postmortem is already being written, while the fix stage or a mitigation runs, and when the Postmortem stage has no usable model. The first write on a bundled example saves a copy of it to `.data/`.
- **Model:** the **Postmortem** stage in Settings → Models (`postmortem/writer.ts`). Until it is changed it uses the Ask stage's model (so Investigate's, when Ask has none either).
- **Limits:** one postmortem per incident; writing again replaces it as soon as it starts. The model has no tools: it reads the record and its evidence only. The export's Owner and Due columns are blank for the team to fill in, and the document ends as a draft until the team has read it.

Most of what Triage shows can be downloaded, so its claims can be checked in other tools and its output moved into them. An **Export** button offers each file where its data is shown:

| Export | Where | Formats |
| --- | --- | --- |
| `incidents` | Incidents toolbar: the rows the filters and sort show, every page | CSV, JSON |
| `incident` | Incident header: the whole stored record | JSON |
| `evidence-logs`, `-spans`, `-metrics`, `-db` | Incident header: the raw evidence, the investigation's and each Ask answer's (`source` column) | CSV, JSON; logs also NDJSON |
| `evidence-source` | Incident header: each source excerpt read, with `cited_by_exposure` marking the files a dependency incident's exposure verdict cites | CSV, JSON |
| `investigation-trace` | Incident header, and the timeline's filter toolbar for the steps on show: the run, steps and thoughts in order, each with its fan-out `lane` where it has one | JSON, NDJSON |
| `fix-patch` | Fix section: the diff exactly as stored, for `git apply` | `.patch` |
| `ask-answers` | Incident header: questions, answers and their cited evidence | Markdown, JSON |
| `postmortem-actions` | Postmortem section: action items with title, description, priority, labels and blank owner and due date, for a Jira or Linear import | CSV, JSON |
| `dependency-findings` | Watch → Dependencies: each advisory the audit finds, and those gone in the last week (`gone_at`), with its incident | CSV, JSON |
| `endpoint-results`, `endpoint-hourly` | Endpoint page: every stored result (48 h) and the hourly summaries (90 days) | CSV, JSON |
| `slo-budget` | Service page → Error budget: each SLO rule and route, with the budget left and the burn over 1 h and 6 h | CSV, JSON |

- **How:** stored data downloads from `GET /api/export/<dataset>?format=…&id=…` (400 for a bad format or params, 404 when there's nothing to export, `Content-Disposition: attachment`, `Cache-Control: no-store`); data that's only on the page (chart series, filtered steps) is built in the browser from the same code. The pieces are under `src/lib/export/`: `datasets/` (what each file holds), `serialize.ts`, `exports.ts` (the server's list) and `components/export-menu.tsx`.
- **Files:** CSV has a UTF-8 BOM and CRLF so spreadsheets read it as written, quotes as RFC 4180 says, and puts `'` before a text cell starting with `=`, `+`, `-` or `@` so it can't run as a formula. Times are ISO 8601 UTC; numbers are raw, with the unit in the column name (`response_ms`). JSON wraps the rows with the dataset, the time and what was exported. Filenames read `<dataset>_<name>_<UTC time>.<ext>`.
- **What's never in one:** columns are a fixed list per dataset, so a new field on a record stays out until a column names it, and secrets (the check's header value, API keys, webhook URLs) are never columns. An export shows no more than the page that offers it.

## Investigation agent

`src/lib/investigation/` holds Stage 2: a `ToolLoopAgent` on the Investigate stage's model (Settings → Models) with seven telemetry tools and a `submit_report` tool. Reports are validated (schema, `reportProblems`, unknown evidence IDs, every service queried, and no root cause resting on a flag that is off: `off-flags.ts`); rejections go back to the model to fix. Tools read from a `TelemetrySource`: the running Shopfront's telemetry, database and code (`live/live-source.ts`), a recorded scenario in `scenarios/`, or an endpoint check's results. The alert brief ends with what the logs say each feature flag is now (the source's `describe().flags`), so code behind a flag that is off is ruled out before a file is read, and `submit_report` holds the report to it: a root-cause verdict whose leading hypothesis cites the record that turned an off flag on, or names that flag in its title or root-cause claim, is sent back. It passes if the claim says the flag is off or ruled out (which is also how it blames what the flag left behind, such as connections it never released), cites a code deploy, or the requests the alert judged may still be the flag's. For an SLO alert that knows the minutes it is burning on, that means the flag went off after they began. Otherwise it means the flag went off less than 15 minutes before the alert, or within an SLO alert's short window when that is longer: the alert fires only while that window burns too, so its long window doesn't count. A flag the source can't place is never checked. (Seen on 2026-11-04: a Page latency false page blamed on FF_STOCK_DIRECT_QUERY, 32 minutes after it was turned off; and the API SLO's 6× alert on the price list gap blamed on the same flag, turned off 26 minutes before the alert after an earlier outage in its 6 h window.) The report rules say a root cause may be the load itself with no file at fault, that a file is named only when the window's traces or logs show its code on the slow path, and that a `slow_queries` row counts only if it ran in the window. For that, `db_diagnostics` reports each statement's `window_calls` and `window_ms`, its calls and time in the 15 minutes before the alert, beside its totals since the statistics were reset, and says in its summary which minutes the window covers: the watch samples `pg_stat_statements` every 30 s (`sampleStatements` in `live/live-source.ts`, kept 3 h in memory) and the diagnostic counts from the sample nearest the window's start, or the oldest one at least a minute old right after a restart, or reports the totals alone and says so. The totals alone had the fix sandbox's hours-old copy of the reviews table topping the list during the traffic rush, and runs blamed it.

**Hypothesis fan-out.** Off by default; Settings → Models → "Check hypotheses in parallel" turns it on for every investigation the app starts (the button, the watch, uptime checks, live ranges and the scripts). It runs in three phases (`fanout/`). A scout on the Lead stage's model (Wonder on Meta's API at high effort until changed) surveys with the read-only tools for up to 8 model steps and proposes 0 to 3 hypotheses. One lane per hypothesis, on the Investigate stage's model, checks it side by side with the others for up to 8 steps (and 4 minutes) and submits a finding (supported, refuted or unclear) citing evidence; lanes start from the scout's evidence and cite it rather than query it again. A merge on the Lead model weighs the findings against all the evidence for up to 6 steps and submits the report through the usual checks. All of it counts against the run's 30 steps and time limit. A scout that fails hands its evidence to the single agent; a lane that fails is an unclear finding with its error; a merge that fails or ends without an accepted report hands the evidence and every finding to the single agent, which finishes with the steps left. This is Triage's own orchestration: Meta's API has no sub-agent primitive, so Triage runs the lanes, and the lead model proposes and merges. The incident records the lead model and its tokens on `run.fanout` (the run's own token fields hold the lanes' and any fallback's), so the cost line prices each at its model's rates, all under Investigate.

**Scenarios and grading.** `scenarios/` holds seven recorded runs: `pool-leak`, `price-gap`, `live-ratings`, `bad-deploy`, `traffic-rush`, `vulnerable-dependency` (see Dependency advisories) and `healthy`. `price-gap` is the price list gap: 500s on `GET /api/products/[id]` after `FF_LIST_PRICES` went on, raised by the Server errors rule and replayed from a real run's telemetry, database diagnostics and Shopfront files. `live-ratings` is the live ratings loop: `GET /api/products` at about a second with no errors after `FF_LIVE_RATINGS` went on, raised by the API latency rule and replayed the same way from a run on 2026-11-01. `bad-deploy` is the bad code deployment: every `GET /api/products/[id]` answers 500 after release `0dfdbac` (`shopfront-release/formatted-price`) is deployed with no flag involved, raised by the Server errors rule and replayed from a run on 2026-11-02 under API-only traffic; the deploy record is the only change in the window, so the expected mitigation is a rollback rather than a flag. `traffic-rush` is the capacity trap: a copy-only release (`417b767`, `shopfront-release/journal-copy`) goes out and a minute later the request rate triples, so every page slows and the Page latency rule fires; nothing is broken, the flags are off, and the right answer is the load with no mitigation. It was recorded on 2026-11-02 from the Normal day profile stepped from 2 to 6 req/s, and the stale reviews rows in `pg_stat_statements` are kept as the live source showed them: they are the bait. Each scenario carries its ground truth as `expected`, which never shows in the scenario's description, the tool descriptions or any query result (`scenarios.test.ts` checks). `grade(report, mitigation, expected, evidence)` in `scenarios/grade.ts` scores a finished run. A root cause hits when the summary or the leading hypothesis (its title and causal chain) names or cites a root-cause file, uses a word from every `mustMention` group, and the proposed mitigation matches. For `price-gap` that is `src/lib/prices.ts`; `product_prices` or the price row in words; stock or join; that the row is missing; and turning off `FF_LIST_PRICES`. For `pool-leak`, `src/lib/stock.ts`; release or leak; pool or connection; and turning off `FF_STOCK_DIRECT_QUERY`. For `live-ratings`, `src/lib/ratings.ts`; a query per product (loop, per product, N+1, sequential and the like); the reviews; that the rating comes from those reviews (average, aggregate, in memory, all reviews, rating, sum and the like: a 2026-11-02 pass of 20 runs named the loop and the reviews every time and spelled out the in-app averaging once, so the rating itself counts); and turning off `FF_LIVE_RATINGS`. For `bad-deploy`, `src/app/api/products/[id]/route.ts` or `src/lib/money.ts`; the currency; the formatter (Intl, NumberFormat, formatPrice or format); the deploy, release or commit; and rolling back `0dfdbac`. The word lists take any phrasing of the same fact, not the scenario author's wording. A healthy scenario hits on any verdict but `root_cause`. A `no_defect` scenario (`traffic-rush`) hits on any verdict whose words name the load (traffic, request rate, rush, capacity and the like) as long as no mitigation is proposed and the root-cause claim, its title or the summary names or cites no source file (a file the symptom or propagation claim cites to show what slowed, a static page's source say, clears it rather than blames it): the mistake being graded is blaming a change that did nothing.

**Benchmark.** `pnpm --filter @triage/web benchmark` runs every scenario 10 times on Spark (Meta's API) and Glimmer (OpenRouter), 3 at a time, and grades each run as above. It reports, per model, the root cause found rate on the fault scenarios, the false-positive rate on the control run (a `root_cause` verdict on `healthy`), the median time from the run's start to its verdict, the median cost per run and the failed runs, each rate with its 95% Wilson interval, then a breakdown by scenario and every miss with its reasons. Runs are investigation only, use the Settings' Investigate effort, and never reach the incident list. `--runs`, `--scenarios` and `--concurrency` change the shape; `--models` takes aliases (`spark`, `wonder`, `glimmer`, `spark-open`) or `provider:model`, each with an optional `@effort`, so `--models spark@low,spark@high` compares efforts. `<lanes>+<lead>` runs the hypothesis fan-out instead, each side a model as above (the lead's effort defaults to the Lead stage's), so `--models spark,spark+wonder,glimmer+wonder` compares the single agent with two fan-outs; a plain model always runs the single agent, whatever the Settings switch says. Results go to `.data/benchmarks/<UTC time>/`: each run's incident in `runs/`, `results.ndjson` as runs finish, and `report.md`. `--report <that folder>` grades the saved runs again with the current ground truth and rebuilds the report, without model calls. It needs `MODEL_API_KEY`, and `OPENROUTER_API_KEY` for Glimmer. Scoring lives in `scenarios/benchmark.ts`. The `bad-deploy` scenario was first benchmarked on 2026-11-02 (`.data/benchmarks/2026-11-02T06-53-30`): 20 of 20 runs found the root cause and proposed rolling back `0dfdbac` on Spark (median 23 s, $0.03 a run) and 20 of 20 with Spark lanes under a Wonder lead (median 72 s, $0.28), no failed runs. The `traffic-rush` trap, benchmarked the same day (`.data/benchmarks/2026-11-02T07-53-21`), first came out at Spark 8 of 20 (median 66 s, $0.15) and Spark lanes under a Wonder lead 13 of 20 (median 115 s, $0.68), with no mitigation proposed in any of the 40 runs. Eight of those misses were the grader's: correct load verdicts that cited the journal page in the propagation claim to show a static route slowed too (regraded, 9 of 20 and 20 of 20). The other ten blamed `src/lib/ratings.ts` off the stale `pg_stat_statements` row (the fix sandbox's hours-old copy of the reviews table, 84 calls at 1.3 s, nothing in the row saying when). After the window columns, the brief's flag line and the two report rules, the same evening's run (`.data/benchmarks/2026-11-02T17-37-52`) is 20 of 20 on both (Spark median 36 s, $0.10; the fan-out 73 s, $0.62), still with no mitigation proposed, and a 10-run pass over the other five scenarios (`.data/benchmarks/2026-11-02T17-47-49`) kept `pool-leak` (9 and 10 of 10), `bad-deploy` (10 and 10) and the control (no false positives) at or near full marks, with `price-gap` at 8 and 8; `live-ratings`, benchmarked for the first time that evening (`.data/benchmarks/2026-11-02T18-07-48`, 10 runs each), is 10 of 10 on both, every run proposing to turn off `FF_LIVE_RATINGS` (Spark median 21 s, $0.05; the fan-out 90 s, $0.53).

## Model-call timeouts and retries

Every model call, in all four stages and the Test connection ping, goes through `retryingFetch` (`src/lib/models/fetch.ts`), given to the provider clients in `languageModel()`. Limits are in `src/lib/models/policy.ts`:

- **Attempt:** 90 s per request (5 min for a local server), up to the whole answer, or for a stream the next bytes. The slowest of 105 recorded Spark 1.3 calls took 28 s.
- **Retries:** 408, 429, 500, 502, 503, 504, network errors and timed-out attempts, 4 attempts in all, waiting a random 0–1 s, 0–2 s, then 0–4 s (a 429's `retry-after` instead, up to 30 s). The AI SDK's own retries are off (`maxRetries: 0`) so the two don't multiply.
- **Stall:** a streamed answer (Ask, the postmortem) fails after 60 s without output once it has started.
- **Run budget:** investigate 10 min, fix 15 min (sandbox included), Ask 5 min, postmortem 5 min, from after a cold host wakes.

A retry that works shows nothing; each run counts them as `modelRetries` (the trace export's `model_retries`). A failure saves a sentence such as "Meta Model API answered HTTP 503 (4 tries)." or "The investigation ran past its 10-minute limit." (`modelErrorText`), which the Overview titles "The model didn't answer in time", "The model's API is overloaded" or "Couldn't reach the model".

## Fix and proof (Stages 3 and 4)

`src/lib/investigation/fix/` runs after a live run's root-cause verdict. The model reads the code and submits exact edits plus a new vitest regression test (`submit_fix`). `prove.ts` checks them in a throwaway copy of Shopfront under the OS temp dir (`fix/sandbox.ts`; node_modules linked, never the app itself). Each test run gets its own throwaway copy of Shopfront's database (`fix/database.ts`): a new database on the same server, built with the app's own Drizzle migrations and filled with the live rows and sequence positions, then dropped. The sandbox's `DATABASE_URL` points at it, so a test may write without touching the real data; a test that opens its own connection is turned back. The database user needs `CREATEDB` (the compose user is a superuser). Three checks:

1. The test runs against the current code and must fail on an assertion.
2. The edits are applied and the test must pass.
3. The patched app must typecheck.

A failed proof goes back to the model with the reasons (up to 4 submissions), and each rejection is kept on `fixRun.rejections`. A proven fix is saved as `fix` (with a git-style diff) and `validation` (each run's command, exit code and output), and the incident moves to `awaiting_approval`. Recorded scenarios stop at the diagnosis: they have no code to run.

**A rolled-back release.** When the mitigation is a rollback (`mitigation.kind` `rollback`, its `target` the release's short sha), the fix stage works from the release commit's tree rather than the live checkout: `read_source` lists and reads files at that commit (`fix/release-tree.ts`, through `git ls-tree` and `git cat-file`, with the harness left out as usual), and the sandbox is that tree exported from git, with the live app's `node_modules` linked in and its generated route types copied as always. The fix and its regression test are proven against the release's code, which is what the PR targets (see Pull request), so the rollback can land on the running store while the fix is still being written. Every other incident reads and proves against the checkout as before.

## Fixes that change stored data

Some bugs leave bad rows behind that a code fix alone doesn't repair: the price list gap leaves products with no `product_prices` row. A fix may then add one migration under `drizzle/` that repairs those rows. Approving it takes an explicit acknowledgment.

- **What counts:** Triage works it out from the edits, not from the model's word alone (`fix/data-change.ts`). A fix changes data when it adds or changes a file under `drizzle/` or ending in `.sql`, or adds upper-case SQL at the start of a statement that writes rows or changes the schema (`INSERT INTO`, `UPDATE … SET`, `DELETE FROM`, `ALTER`, `CREATE` or `DROP` of a table, index and the like, `TRUNCATE`). It also counts when the model says the fix touches data (`touchesData`). Drizzle query-builder writes (`db.insert(...)`) don't count. The result is saved on the fix as `dataChange` (`detected`, `reasons`, `files`, `unproven`); older fixes have it worked out from their patch, without the regression test.
- **The migration:** the model creates it with an edit whose `find` is empty, named `drizzle/<words>.sql`. Triage renames it to the next number (`drizzle/0005_backfill_product_prices.sql`) and writes its entry in `drizzle/meta/_journal.json` itself (`fix/migration.ts`), with a `when` later than the last entry's, since Drizzle's migrator skips older ones. The model never edits the journal, and no snapshot is written. Triage sends back a fix with more than one new migration, or one whose migration changes the schema (`ALTER`, `CREATE`, `DROP` go through `db:generate`).
- **Never run:** Triage never runs the SQL. The sandbox proves the code half as usual but runs no migration, so the Fix section and the approve dialog mark the migration and the journal "Not proven in the sandbox".
- **The acknowledgment:** the approve dialog shows a "Changes stored data" banner with the reasons, the SQL and the journal entry. Approve stays disabled until "I've reviewed the data change" is ticked. `POST /api/incidents/<id>/approval` answers 409 to an approval of such a fix unless it sends `"dataReviewed": true`, and the approval records `dataReviewed`. Deny needs nothing.
- **The PR:** its description opens with a warning that the data change wasn't proven, the reasons, and a checklist: review the SQL, run it against a copy of production data, and note that merging ships it with the deploy.

## Pull request (Stage 5)

Approving a proven fix opens a draft PR (`fix/pull-request.ts`, run after the approval response):

1. Make a temporary git worktree on a new `triage/<incident>` branch, cut from the remote's default branch (or `TRIAGE_PR_BASE`); when the mitigation rolled back a release, from that release's branch (`mitigation.branch`), since the fix was proven against the release's code.
2. Apply the proven patch under the app's folder, commit, and push to `origin`.
3. Run `gh pr create --draft` with the diagnosis and sandbox proof as the description.

The checkout you work in is never touched, and nothing merges by itself. The incident shows the PR's progress, its link, or why it failed with a Retry (`POST /api/incidents/<id>/pull-request`). Only fixes Triage proved get a PR; approving a bundled example only records the decision.

**Deny with feedback.** Deny opens a dialog with one optional field, "What should Triage do differently?" (up to 500 characters). Empty, it denies as before. With text, the feedback is saved as the approval's reason and, when the fix was proven on the live Shopfront, the button reads "Deny and try again": the denied attempt (fix, proof, run and approval) is archived on `incident.fixAttempts`, the incident goes back to diagnosed, and the fix stage runs again (`fix/rerun.ts`) with every denied attempt's feedback and patch in its prompt (`fix/feedback.ts`). `submit_fix` turns back a patch that repeats a denied one (byte-equal, or the same code hunks ignoring the test file) before the sandbox, without spending a submission. A proven rerun arrives as "Attempt 2", awaiting approval as usual; the Fix section lists earlier attempts with their feedback, proof and diff. On a bundled example or a recorded scenario the feedback is recorded and the dialog says no new attempt follows.

PRs are drafts so they can't be merged by accident. Don't merge them into the main branch: that removes the planted bug, and the commit message would put the answer in the history Triage reads.
